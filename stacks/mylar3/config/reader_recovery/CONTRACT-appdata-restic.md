# App-only Restic recovery

This prospective contract replaces full-tree preservation in the configured
Root recovery routes. The transport implementation alone grants no backup,
reader-stop, publication, restart or cleanup authority. Keep those routes held
until their owning factories and installed-source checks implement this contract.

The fixed retained-pack policy v3 and standalone policy v3 implement the host
transport. Standalone keeps its four original source roles but sends only Native
and reader app data to Restic. Its selected retained source and existing target
remain in place. The original standalone observation type, complete SQL proof,
snapshot and restored-node descriptors continue through terminal verification
and body retirement. Legacy copy fixtures retain their default interface and
provide no configured live backup proof. The configured archive route still
requires its own Root-to-proof-child integration.

## Source coverage

The owning Parent retains its complete original source census, hashes, metadata,
aliases, namespaces and physical custody through final acknowledgement. It owns
writer exclusion and a consistent database boundary. Native configuration,
worker state and the complete effective reader configuration remain separate
roles. Standalone backs up the complete Native `/config` mount, including app
files outside DATA. Nested Native or Reader `/config` mounts hold until their
effective multi-origin source coverage has a reviewed profile. Its effective configuration must belong to that original
source census. Reader state stays host-only during Native directory-successor
checks and remains in the complete terminal preservation frame. The retained-pack profile selects an external Worker configuration through an
explicit v2 file scope when it lies outside the three app-data trees. This scope
names the exact original bounded JSON object and restores only
`worker_configuration/configuration.json`. It never enumerates or backs up the
source parent directory. The same original full signature, hash, attributes and
restored-file descriptors stay in the genuine backup observation through terminal
closure. Files already covered by a tree must survive its app-data classifier.
Nested mounts below the Worker state root hold. Archive recovery also retains its actual original and
custody archives.

Back up configuration, databases with required companions, operational controls
and application caches. Exclude library files, completed downloads and held
book/page payloads from Restic and disposable restores. Hash those originals in
place. Native metadata artwork remains application data. A media exclusion
changes storage coverage, never source admission or preservation obligations.
Unknown file kinds, escaping links and unsupported metadata hold the operation. Unknown Native archives also hold. A diagnostic carepackage requires its bounded complete app-member schema and content checks.

## Repository and restore

Use the existing Restic owner, credentials and repository. The first supported
Root profile uses the existing container named `restic`, its original immutable
container identity and local `/repository` mount. Bind its image, process,
configuration and mounts before use. This profile does not initialize a
repository, alter retention, copy credentials or create a replacement mount.
Remote repository backends require their own reviewed lifetime witness.

Stream only enumerated app files and a bounded source index to the existing
Restic CLI. Do not stage a plaintext full-tree backup. Respect repository locks
and the original operation deadline. Record the actual successful snapshot ID,
unique operation tag, exact artifact path, size and SHA-256. A partial stdin
snapshot, caller JSON or historical restore receipt supplies no owning proof.

Independently read the app artifact back from that exact encrypted snapshot.
Restore into an exclusively created private location outside every live source.
Accept only the exact ordered regular-file members and source index. Freeze the process-local selection before codec callbacks. Independently decode persisted index bytes and compare them with that original selection. Never use
archive extraction paths or follow archive links. Recreate only enumerated
directories and supported local application links. Retain born file and directory descriptors across metadata changes, inventory and SQL callbacks. Use held parent descriptors for exclusive creation and retain original output ancestry across backup. Verify the complete restored
namespace, hashes, independent file identities, attributes and every required
database through detached SQL scratch. No media bytes may appear in the restore.

One encrypted Restic snapshot and one independent app-data restore replace the
old pair of plaintext full copies. Bind the actual encrypted snapshot file and
its original repository ancestry through final closure. A directory named
`backup` or a healthy application is not encrypted recovery proof. Do not present
an app-only restore as a full-media copy or a full isolated-service recovery drill.

## Owning integration and completion

Only the original source-backed factory may publish its existing typed,
process-local backup observation after all checks pass. Seal the app selection,
excluded-media census, snapshot and restore witnesses with the complete original
source and primitive callable registry. Final closure must check these same
witnesses without receipt hydration, deadline renewal or expected-state rebasing.
Keep source-backed SQL, alias, namespace, terminal and reader-preservation checks.

Changing storage coverage requires matching producer, consumer, installation,
profile and source pins. Neither an ordinary Native rollout nor a standalone
transport test establishes this integration. Qualify the actual filesystem and
Restic path before a fresh configured owning attempt. Never replay a spent nonce.

After verified completion, retain compact receipts and the actual snapshot ID
privately. Remove disposable app restores, SQL staging and obsolete operation
backup copies. Preserve unresolved originals, durable failure histories and
active source suppliers. The Restic owner retains its normal snapshot policy.
Task cleanup never authorizes `forget` or `prune`.
